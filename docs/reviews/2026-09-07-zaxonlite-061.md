# Zaxonlite v0.6.1 dependency review — 2026-09-07

Sibuna now pins the released Zaxonlite v0.6.1 archive and its verified Zig content hash.
The existing `Node` and `Embedded` APIs remain compatible; no Sibuna request-handler or
persistence API change was needed. README and SID 0005 name the new version.

## Fix review

[Upstream PR #6](https://github.com/insanai/zaxonlite/pull/6) addresses the ordering defect
reported in [issue #5](https://github.com/insanai/zaxonlite/issues/5). A leader could capture
SQL against its applied state while an earlier log entry was still outstanding, creating a
transaction whose base would be stale when chosen. The new host admission waits until every
slot below the next proposal is applied, before executing SQL. The mutex remains held from
admission through append; after a condition-variable wake, failure and leadership are checked
before accepting a settled frontier. The lower-level Node also refuses premature capture.

Leader and linearizable reads wait for the inherited prefix, and read fences cover that
prefix. A lagging leader continues recovery from peers. Chain validation still fails closed
and now reports which base checks differ. The release pins Paxos 0.6.1 at commit
`701e167d5e77c2da019ec5b99a1e83abbd907acd`, with inherited-prefix proposal gating enabled.

The new admission checks operate on the background database path. Source review found no
new steady-state admission allocation, fsync or network round trip. Waiting during recovery
is intentional. This does not mean zero CPU overhead: comparisons and waiter accounting have
costs, and the measurements below do not establish a universal performance bound.

## Local validation

- Sibuna tests: 86/86 with storage; 86/86 with clustering; 83/83 without storage.
- Formatting/style checks and SID/book compilation passed.
- Original standalone reproduction, unchanged: ten fresh three-node clusters, 2,549
  acknowledged writes, no ChainMismatch. Every client acknowledged writes in every round.
  Raw sanitized logs and binary/script hashes are in
  [`zaxonlite-061-validation-20260907.json`](../../benchmarks/results/zaxonlite-061-validation-20260907.json).
- Upstream `zig build test-cluster -Doptimize=ReleaseFast` passed both the mandatory
  recovery scenario and the targeted inherited-slot takeover scenario. The new leader
  waited 4,144 ms for the deliberately delayed slot; recovered and new writes appeared
  exactly once and the restarted data voters agreed. The command log is preserved in
  the validation JSON above.
- The full Sibuna distributed matrix passed, including shared sessions, authenticated WAF
  blocking, issuer-bound challenge verification, replicated bans, leader-loss serving and
  new ban propagation after failover. External log checks found no chain mismatch.

## Distributed measurements

Apple M1, macOS 26.6.2, Zig 0.16.0, ReleaseFast, three local processes and six external clients.
These are batch HTTP rates with the existing in-memory admission path, not durable SQL rates.

| Case | Admitted requests/s | Ban propagation | New ban after leader loss |
|---|---:|---:|---:|
| Gate, no storage | 45,383 | — | — |
| Shield, no storage | 44,853 | — | — |
| Shield, PSK | 44,374 | 51.5 ms | 411.5 ms |
| Shield, mTLS | 44,479 | 124.4 ms | 594.2 ms |

After leader loss, the two survivors served about 39,500 requests/s with each transport.
Propagation values are individual checks, not latency percentiles. The earlier PSK result
was about 45,500 requests/s; these separate local runs are broadly similar but do not isolate
a small dependency-induced regression. The earlier mTLS run failed before measurement.

The timestamped run is
[`distributed-latest-20260907T134310Z.json`](../../benchmarks/results/distributed-latest-20260907T134310Z.json).
The harness now records the dependency URL/hash and checks node logs outside timed batches;
no benchmark hooks or timers were added to the daemon. Historical v0.6.0 failure logs and
measurements remain intact.

## Scope

The reported failure was not observed with the released fix in these checks. This is not
proof over all schedules or certification of a WAN deployment. The update does not repair
already inconsistent v0.6.0 data directories; this validation used fresh clusters. High-volume
incident persistence, queue overload accounting, batching/aggregation, global quotas and
other deployment limitations identified in the original SID review remain separate work.
