# SID 0002–0006 implementation review — 2026-09-07

The review found correctness and measurement defects despite the original 81-test suite
passing. The fixes below are implemented. This is not a proof of universal algorithmic
optimality, a formal cryptographic audit, or certification of a globally deployed edge WAF.

The historical v0.6.0 storage failure below is addressed by the subsequent
[v0.6.1 dependency review](2026-09-07-zaxonlite-061.md). Original measurements and failure
logs are retained as evidence; see that follow-up for current validation.

## Implemented fixes

| Area | Finding and correction |
|---|---|
| SID 2: request ordering | Session cookies bypassed both WAF and terminal denials. Policy now runs before session admission; live HTTP regressions cover an authenticated encoded attack and a deny rule. |
| SID 2: HTTP framing | Invalid lengths, control bytes and standalone Transfer-Encoding could produce ambiguous forwarding. Reject unsupported encoding and malformed fields, preserve valid extension method names, and fail truncated bodies. Locally answered partially buffered bodies cannot reuse the connection. |
| SID 3: policy | Dynamic rules appended after generic browser rules could be shadowed. Database rules now precede file/default rules. Anchored literal matching is exact. Rule names are bounded to 128 bytes and exclude control characters. |
| SID 4: memory | Dense signature capacities were oversized. Derive a safe capacity from total pattern lengths, retaining one transition per byte. Engine size falls from approximately 1.74 MB to 766,672 bytes, about 56%. |
| SID 4: normalization | Encoded payloads after byte 2048 bypassed canonicalization. The full 8 KB inspection prefix is now eligible, using one caller buffer for shrinking passes. |
| SID 4/6: GCRA | Forcing hashes odd wasted half the shards. Remap only zero. Round the emission interval upward and preserve the configured burst; rate zero denies. Saturation no longer evicts active quota cells. Shard locks are cache-line aligned and spin on reads before retrying a contended write. |
| SID 4: bans | Separate key and expiry loads could observe a mixed replacement. Readers validate a versioned atomic snapshot. This has real synchronization costs and is not wait-free. |
| SID 5/6: publication | Acquire/release operations on different atomics did not establish the claimed total ordering. Use sequentially consistent pin/publication operations. Copy the response rule name and release the slot before proxy I/O. |
| SID 5: arena lifetime | The spare-versus-active comparison selected the same arena repeatedly. Each physical engine slot now has its own arena. Repeated reload regressions check retained rule strings. |
| SID 5: reloads | Counts and maximum timestamps missed updates. SQL triggers maintain a revision for insert/update/delete. A failed rebuild does not acknowledge it. Expiring reputation independently triggers reload. |
| SID 5: initialization | Schema setup now commits as one transaction. Bounded retries cover idempotent startup work, not ambiguous incident writes. This reduces consensus round trips but does not repair the v0.6.0 storage-chain failure. |
| SID 2/5: replay | Sharing challenge keys allowed one solution to be spent on different nodes. In cluster mode derive the challenge key from node identity at startup; keep token keys shared. Verification must route back to the issuer. Spent state still disappears on restart. |
| SID 6: adaptation | Flooring the observed/baseline ratio undercharged fractional loads. Apply ceiling division before ceiling-log2; 15/s over a 10/s baseline now adds two bits. |
| SID 6: claims | Withdraw the unconditional “cheating never pays” lemma and unsupported browser timing table. Fixed-commitment sampling probabilities do not by themselves bound Fiat–Shamir grinding or work reuse. Published oracle-model results are not a concrete implementation audit. |

## Benchmark corrections

The primitive harness is a separate executable. It uses seven timed batches, untimed warmup,
and untimed state reset before each batch. The previous spent-set batches reused tags and
mostly measured duplicate rejection; insert failures are now fatal to that benchmark. Bot
comparisons now search identical pattern sets with any-match semantics. Compiler barriers
keep pure verification calls in the loops without per-operation clocks. Unsupported competitor
cost models were removed. Allocation activity is not instrumented, so `alloc_bytes` is null;
allocation-free primitives are an API/source finding. Exact table sizes use `@sizeOf`.

The external Python harness starts three actual daemon processes and six load-client
processes, consumes and checks every HTTP response, and records batch throughput. It compares
Gate, Shield, and clustered Shield, with separate loopback PSK and mutual-TLS cases. It checks
shared sessions, authenticated WAF denial, issuer-bound solution rejection, ban propagation,
serving after elected-leader loss, and propagation of a fresh ban after failover. Failed cases
are retained with logs and make the harness exit nonzero. No benchmark instrumentation is
linked into the request handler. Production metrics, locks, snapshot counters and incident
enqueue still have costs.

## Historical finding: distributed storage chain failure in v0.6.0

The expanded multi-process runs exposed intermittent `ChainMismatch` errors inside the
pinned Zaxonlite v0.6.0 dependency, followed by `RemoteOperationFailed` and failed daemon
initialization. This occurred under both transports across attempts. Consolidating migrations
and retrying startup did not eliminate it. The recorded final matrix includes a successful PSK
cluster run and a failed mutual-TLS cluster startup. Do not treat the cluster build or passing
unit tests as evidence of production readiness.

Reproduce with `python3 benchmarks/distributed.py`; see the failed row and captured node logs
in `benchmarks/results/distributed-latest-20260907T105759Z.json`. Certificate identities in the harness use the
transport-required `zaxon-node-<id>` common names and a temporary trusted CA.

Follow-up isolation reproduced the failure in three stock Zaxonlite processes, without
Sibuna, its Embedded integration, TLS, FTS or vector tables. Three concurrent clients start
during election, execute `CREATE TABLE IF NOT EXISTS b(id INTEGER PRIMARY KEY, v INTEGER);
INSERT INTO b(v) VALUES(1);`, then issue linearizable count queries. The fifth fresh cluster
reported `ChainMismatch` on all three nodes after only one acknowledged application write.
This establishes an upstream failure, although the precise internal race remains unknown.
The chain checks in `accountCommitted` and image replay warrant diagnostic instrumentation;
the earlier suspicion about capture-slot accounting is not a proven explanation.

Filed [Zaxonlite issue #5](https://github.com/insanai/zaxonlite/issues/5) with the complete
standalone script, logs, environment and expected behavior. The checked-in diagnostic is
`benchmarks/repro_zaxonlite.py`; run it with `--zaxon /absolute/path/to/zaxon --rounds 10`.
A subsequent ten-round validation completed without reproducing the failure, confirming
that the test is scheduling dependent. Logs and isolated measurements are preserved in
`benchmarks/results/zaxonlite-isolation-20260907.json`. No dependency cache files were
modified, and no chain validation was bypassed. A fix and upstream fault-suite validation
are still required before treating distributed storage as production ready.

### Storage capacity is distinct from request throughput

The dependency's unmodified `bench-cluster` completed 300 sequential 256-byte writes and
300 reads with each transport, using full sync, Zig 0.16.0 and ReleaseFast on Apple M1:

| Transport | Durable transactions/s | Write p50 | Linearizable reads/s | Maximum node RSS |
|---|---:|---:|---:|---:|
| TLS | 63 | 15.857 ms | 8,608 | 17 MiB |
| PSK | 65 | 15.153 ms | 10,304 | 12 MiB |

These isolated runs support modest policy/reputation traffic, subject to fixing the
replication failure; they do not establish sustained incident capacity. Sibuna's current
storage thread performs one nearest-campaign query and one replicated transaction per
incident. `incident_batch` bounds work per tick; it does not combine multiple incidents
into one transaction. Its 512-entry queue drops new records when full, and slow draining
can delay policy polling. Thus the roughly 45,000 in-memory HTTP requests/s result cannot
be interpreted as 45,000 durable incident records/s. High-volume forensics needs measured
batching/aggregation, overload accounting and sustained ingestion validation. SQL remains
off the request path, and the added reproducer introduces no daemon instrumentation.

## Validation and deployment boundary

The standard tests pass with storage enabled and disabled, and with clustering enabled;
format/style, all SID documents, the SID index/site, and the book are checked. Exact counts
and current benchmark measurements are reported with the completed review. Results retain
host, compiler, source/binary fingerprints and revision metadata.

Gate and Shield are the two surfaces; replicated edge deployment is an option for either.
Competitor names and unsupported parity claims were removed from product documentation and
SID metadata, including the SID 0004 slug. Feature tables compare Sibuna's own surfaces.

Still unimplemented or unproven: WAN behavior, client-facing TLS termination, HTTP/2, global
rate quotas, durable replay state, volumetric network mitigation, and full language-parser
inspection. Bodies beyond 8 KB, oversized encoded fields, excluded structural headers and
bytes omitted by a forward-auth ingress can evade inspection. Blocking worker concurrency,
queue loss under overload, public non-cryptographic table hashes, and bounded ban eviction
also require deployment-specific capacity and adversarial testing. Primitive timings alone
cannot justify fleet throughput or an “equivalent to a global edge service” claim.
